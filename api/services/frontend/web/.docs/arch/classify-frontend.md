# Classify / Clarification System (Frontend)

> Two parallel feature systems sharing the same domain. **Classify** is a one-shot trigger that analyzes unlinked tasks and bulk-assigns context via the AI pipeline — it surfaces a modal dialog from the task board. **Clarifications** is a queue-based review loop where the backend emits questions for user decisions (context assignment, stale tasks, ambiguous deadlines, etc.) — it has its own full-page view with a card-based queue UI. Both systems share the `ClarificationItem` type and the `clarificationService`.

## Core Types

### `types/clarification.ts`

```typescript
import type { ClarificationKind, ClarificationStatus } from './enums'

export interface ClarificationItem {
  id: string
  kind: ClarificationKind              // which clarification template to render
  status: ClarificationStatus

  claudeGuess?: Record<string, unknown>
  reasoning?: string                   // optional explanation shown below the question
  answerOptions: Record<string, unknown>  // typed per-kind payload (see generated types below)
  answer?: Record<string, unknown>
  priorityScore: number
  snoozedUntil?: string
  createdAt: string
  resolvedAt?: string
}

export interface ClarificationCountResponse {
  count: number
}
```

## File Map

### Services

- `services/classifyService.ts` — **classifyService** — POST /api/v1/tasks/classify; returns ClassifyAccepted
- `services/clarificationService.ts` — **clarificationService** — full CRUD for clarification items: queryQueue, queryByID, countPending, resolve, snooze, dismiss

### Stores

- `stores/clarificationStore.ts` — **useClarificationStore** — Pinia store managing the clarification queue: `items[]`, `currentIndex`, `pendingCount`; exposes resolve/snooze/dismiss which mutate state in-place and call clarificationService

### Composables

- `composables/useClarification.ts` — **useClarification** — thin wrapper around useClarificationStore; calls `fetchQueue()` on mount; exposes reactive refs + actions for page-level use

### Components

- `components/tasks/ClassifyDialog.vue` — **ClassifyDialog** — modal dialog triggered from TaskBoardView; calls classifyService.classify(); three UI states: confirm / running→result / error
- `components/clarifications/ClarificationCard.vue` — **ClarificationCard** — renders a single ClarificationItem; switches UI per `item.kind` (10 variants); emits `resolve(answer)`, `snooze(hours)`, `dismiss`
- `components/clarifications/ClarificationSession.vue` — **ClarificationSession** — queue shell: iterates store items with progress dots and slide animation; delegates actions to store via handleResolve/handleSnooze/handleDismiss

### Views

- `views/ClarificationView.vue` — **ClarificationView** — full-page clarification review; mounts useClarification (triggers fetchQueue); renders ClarificationSession + PageHeader with pending count badge and refresh button
- `views/TaskBoardView.vue` — **TaskBoardView** (cross-domain) — hosts `<ClassifyDialog>` and the "Classify" trigger button in the task board header

### Layout / Navigation

- `components/layout/AppSidebar.vue` — **AppSidebar** (cross-domain) — fetches pending count on mount, re-polls every 60s via `useClarificationStore().fetchPendingCount()`; shows badge on Clarifications nav link

### Router

- `router/index.ts` — `{ path: '/clarifications', name: 'clarifications', component: ClarificationView }` (lazy-loaded)

## Impact Callouts

### ⚠ ClarificationItem (`types/clarification.ts`)
Changing this interface shape affects:
- `stores/clarificationStore.ts` — `items: ref<ClarificationItem[]>`, `currentItem` computed, all store methods iterate/index items array
- `composables/useClarification.ts` — re-exports `currentItem` and `items` as reactive refs
- `components/clarifications/ClarificationCard.vue` — prop `item: ClarificationItem`; template binds `item.question`, `item.reasoning`, `item.kind`, `item.answerOptions`, `item.createdAt`
- `components/clarifications/ClarificationSession.vue` — passes `currentItem` as `:item` prop to ClarificationCard; iterates `items` for progress dots
- `services/clarificationService.ts` — deserializes all API responses as `ClarificationItem`; resolve/snooze/dismiss return updated items

### ⚠ ClarificationKind enum (`types/enums.ts`)
Adding or renaming a kind affects:
- `components/clarifications/ClarificationCard.vue` — v-if chain switches on `item.kind` for all 10 variants; missing kind falls through to generic "Acknowledge" fallback
- `types/enums.ts` — `ClarificationKindLabels` and `ClarificationKindColors` maps must be extended for every new kind
- Backend Go source `clarificationbus/options.go` — must have matching kind constant and options struct (then regenerate via tygo)

### ⚠ answerOptions shape / generated types (`types/generated/clarification-options.ts`)
Changing any options interface breaks:
- `components/clarifications/ClarificationCard.vue` — reads `options.value.available_contexts` (ContextAssignmentOptions), `options.value.suggested_context`, `options.value.interpretations` (AmbiguousActionOptions); currently cast via `as Record<string, unknown>` with inline `ContextRef` type — NOT using the generated interfaces directly
  - **⚠ Note:** The card has its own local `type ContextRef = { id: string; title: string }` duplicate instead of importing from `types/generated/clarification-options.ts`. If you rename fields in the generated type, also update the inline type in ClarificationCard.vue line 32
- `services/clarificationService.ts` — `resolve(id, answer)` sends `answer` as `Record<string, unknown>`; no compile-time checking of answer shape vs kind

### ⚠ ClassifyAccepted (`services/classifyService.ts`)
Changing this response shape affects:
- `components/tasks/ClassifyDialog.vue` — `result: ref<ClassifyAccepted | null>`; template renders `result.message`

### ⚠ resolve answer payload (runtime contract, not type-checked)
The `answer` object sent to `clarificationService.resolve()` is `Record<string, unknown>`. Each kind has an implicit shape:
- `context_assignment` → `{ context_id: string }`
- `inactivity_prompt` / `stale_task` → `{ action: 'extend' | 'close' | 'note', note?: string }`
- `ambiguous_action` → `{ selected: number }` (index into interpretations)
- `ambiguous_deadline` → `{ due_date: string }` (ISO string)
- `new_context` → `{ action: 'confirm' | 'merge' }`
- `context_debrief` / `task_debrief` → `{ response: string }`
- `voice_reference` → `{ resolved_text: string }`
- fallback → `{ acknowledged: true }`

## Cross-Domain Dependencies

- `stores/toastStore.ts` — `useClarificationStore` calls `toast.success()` / `toast.error()` for every user action
- `components/layout/AppSidebar.vue` — imports `useClarificationStore` directly (not via composable) to drive the pending count badge; polls every 60s
- `components/layout/PageHeader.vue` — used in ClarificationView for title + subtitle + refresh button slot
- `components/shared/LoadingSpinner.vue` — ClarificationSession renders during initial load
- `components/shared/EmptyState.vue` — ClarificationSession renders when queue is empty
- `views/TaskBoardView.vue` — hosts ClassifyDialog; refreshes task list after classify completes
- `date-fns` (npm) — `ClarificationCard` uses `formatDistanceToNow` to render relative age

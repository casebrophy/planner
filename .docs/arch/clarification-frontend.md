# Clarification Frontend System

> The clarification feature presents a prioritized queue of decision-prompts to users for resolving ambiguities in their planning data. Items flow through fetch → session → resolution loop, with kind-specific UI rendering (context assignment, stale tasks, debriefs, etc). State is managed by Pinia store with optimistic dismissal/snoozing; service layer abstracts REST API interactions. Each clarification kind (10 total) maps to distinct answer shapes and UI controls.

## Core Types

### ClarificationItem
```typescript
interface ClarificationItem {
  id: string
  kind: ClarificationKind
  status: ClarificationStatus
  subjectType: string
  subjectId: string
  question: string
  claudeGuess?: Record<string, unknown>
  reasoning?: string
  answerOptions: Record<string, unknown>
  answer?: Record<string, unknown>
  priorityScore: number
  snoozedUntil?: string
  createdAt: string
  resolvedAt?: string
}
```

### ClarificationKind
```typescript
type ClarificationKind =
  | 'context_assignment'   // Task needs context link
  | 'stale_task'           // Task inactive, confirm status
  | 'ambiguous_deadline'   // Due date unclear
  | 'new_context'          // New context candidate confirmation
  | 'overlapping_contexts' // Multiple matching contexts
  | 'ambiguous_action'     // Voice/input multiple interpretations
  | 'voice_reference'      // Corrected text transcription
  | 'inactivity_prompt'    // Check inactive item still relevant
  | 'context_debrief'      // End-of-context reflection prompt
  | 'task_debrief'         // Post-completion task reflection
```

### ClarificationStatus
```typescript
type ClarificationStatus = 'pending' | 'snoozed' | 'resolved' | 'dismissed'
```

### ClarificationCountResponse
```typescript
interface ClarificationCountResponse {
  count: number
}
```

## File Map

### Types
- `types/clarification.ts` — **ClarificationItem**, **ClarificationCountResponse**
- `types/enums.ts` — **ClarificationKind** (10 variants), **ClarificationStatus**, **ClarificationKindLabels**, **ClarificationKindColors**
- `types/generated/clarification-options.ts` — **ContextRef**, **ContextAssignmentOptions**, **NewContextOptions**, **AmbiguousActionOptions**, **AmbiguousDeadlineOptions** (generated by tygo from `business/domain/clarificationbus/options.go` — DO NOT EDIT)

### Stores
- `stores/clarificationStore.ts` — **useClarificationStore**
  - State: `items: ClarificationItem[]`, `total`, `loading`, `error`, `currentIndex`, `pendingCount`
  - Getters: `currentItem`, `hasNext`, `isEmpty`, `progress`
  - Actions: `fetchQueue()`, `fetchPendingCount()`, `resolve(id, answer)`, `snooze(id, hours)`, `dismiss(id)`

### Services
- `services/clarificationService.ts` — **clarificationService** (plain object, not factory-based)
  - `queryQueue(params): Promise<QueryResult<ClarificationItem>>` — GET `/api/v1/clarifications`
  - `queryByID(id): Promise<ClarificationItem>` — GET `/api/v1/clarifications/{id}`
  - `countPending(): Promise<number>` — GET `/api/v1/clarifications/count`
  - `resolve(id, answer): Promise<ClarificationItem>` — POST `/api/v1/clarifications/{id}/resolve`
  - `snooze(id, hours?): Promise<ClarificationItem>` — POST `/api/v1/clarifications/{id}/snooze` (default 24h)
  - `dismiss(id): Promise<ClarificationItem>` — POST `/api/v1/clarifications/{id}/dismiss`

### Composables
- `composables/useClarification.ts` — **useClarification**
  - Returns: `{ items, total, loading, error, currentItem, isEmpty, progress, pendingCount, resolve, snooze, dismiss, refresh }`
  - Calls `store.fetchQueue()` on mount; pending count polling is handled globally by AppSidebar (60s interval)

### Components
- `components/clarifications/ClarificationCard.vue` — **ClarificationCard**
  - Props: `item: ClarificationItem`
  - Emits: `resolve(answer: Record<string, unknown>)`, `snooze(hours: number)`, `dismiss()`
  - Renders kind-specific UI with distinct answer shapes per kind (context picker, stale task actions, deadline input, debrief textarea, etc.)
  - Always shows 24h snooze and dismiss buttons; displays question, reasoning, age, color-coded kind badge

- `components/clarifications/ClarificationSession.vue` — **ClarificationSession**
  - No props
  - Composes store + ClarificationCard; shows progress counter and animated card transitions
  - Handles resolve/snooze/dismiss events, calls store methods
  - Shows LoadingSpinner (initial load), EmptyState (queue empty), or card carousel

### Views
- `views/ClarificationView.vue` — Route `/clarifications` — PageHeader with pending count subtitle, refresh button; mounts ClarificationSession

## Impact Callouts

### ⚠ ClarificationItem (`types/clarification.ts`)
Changing interface shape affects:
- `components/clarifications/ClarificationCard.vue` — parses `answerOptions`, reads `claudeGuess`, `reasoning`; kind-specific answer rendering breaks if fields renamed
- `stores/clarificationStore.ts` — array operations and type assertions at compile time
- Backend API — `/api/v1/clarifications` endpoint must match; new fields require DB migration

### ⚠ ClarificationKind (`types/enums.ts`)
Adding/removing kinds affects:
- `components/clarifications/ClarificationCard.vue` — one `v-if` branch per kind for UI rendering; missing kinds fall through to generic "Acknowledge" fallback (loses specificity, not broken)
- `ClarificationKindLabels` / `ClarificationKindColors` maps — must include all kinds; missing entries display raw string / default gray
- Backend `clarificationbus` — must generate matching kind values

### ⚠ ClarificationStatus (`types/enums.ts`)
Changing status values affects:
- `stores/clarificationStore.ts` — `fetchQueue()` filters by `status=pending`; changed value breaks queue loading
- Backend filter parsing — must accept same string values

### ⚠ resolve/snooze/dismiss signatures (`stores/clarificationStore.ts`)
Changing parameter shapes affects:
- `components/clarifications/ClarificationSession.vue` — calls these in event handlers; errors are silent (no toast shown if handler throws)
- `services/clarificationService.ts` — request body shapes must stay in sync

## Cross-Domain Dependencies

- **toastStore** — `clarificationStore.ts` uses `useToastStore()` for success/error feedback on resolve/snooze/dismiss
- **Shared components** — `ClarificationSession.vue` uses `LoadingSpinner`, `EmptyState`; `ClarificationView.vue` uses PageHeader
- **AppSidebar** — polls `fetchPendingCount()` on 60s interval for the nav badge; clarification domain does not poll itself
- **contextStore** — `ClarificationCard.vue` uses context list for the `context_assignment` kind picker
- **services/client.ts** — clarificationService uses `request()` for all HTTP calls

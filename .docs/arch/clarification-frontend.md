# Clarification System — Frontend

> The clarification queue is a user-facing workflow that surfaces decision points generated by the backend's clarification engine. The frontend displays clarifications sorted by priority, handles kind-specific UI for different clarification types (context assignment, deadlines, debriefs, etc.), collects user responses, and sends them back to the API. The system uses Pinia for state management and handles both single-item resolution and batch queue navigation.

## Core Types

### ClarificationItem (types/clarification.ts)
```typescript
import type { ClarificationKind, ClarificationStatus } from './enums'
import type {
  ContextAssignmentOptions,
  NewContextOptions,
  AmbiguousActionOptions,
  AmbiguousDeadlineOptions,
} from './generated/clarification-options'

export type ClarificationAnswerOptions =
  | ContextAssignmentOptions
  | NewContextOptions
  | AmbiguousActionOptions
  | AmbiguousDeadlineOptions
  | null

interface ClarificationItem {
  id: string
  kind: ClarificationKind
  status: ClarificationStatus
  subjectType: string
  subjectId: string
  question: string
  claudeGuess?: Record<string, unknown>
  reasoning?: string
  answerOptions: ClarificationAnswerOptions   // typed union, not Record<string, unknown>
  answer?: Record<string, unknown>
  priorityScore: number
  snoozedUntil?: string
  createdAt: string
  resolvedAt?: string
}
```

Main model transported between API and frontend. The `kind` enum determines which UI component branch renders. The `answerOptions` field is now a typed discriminated union — each kind deserializes to a known interface rather than a generic record.

### ClarificationKind (types/enums.ts)
```typescript
import type { ClarificationKindValue } from './generated/clarification-kind'

export const ClarificationKind = {
  ContextAssignment: 'context_assignment',
  StaleTask: 'stale_task',
  AmbiguousDeadline: 'ambiguous_deadline',
  NewContext: 'new_context',
  OverlappingContexts: 'overlapping_contexts',
  AmbiguousAction: 'ambiguous_action',
  VoiceReference: 'voice_reference',
  InactivityPrompt: 'inactivity_prompt',
  ContextDebrief: 'context_debrief',
  TaskDebrief: 'task_debrief',
} as const satisfies Record<string, ClarificationKindValue>

// ClarificationKind is the authoritative TypeScript type — derived from the generated union.
// If Go adds a new kind, ClarificationKindLabels and ClarificationKindColors below will
// produce a TypeScript error until they are updated.
export type ClarificationKind = ClarificationKindValue
```

Enum of all 10 clarification types. Uses `satisfies Record<string, ClarificationKindValue>` to ensure the const object stays in sync with the generated Go union. The type alias is now `ClarificationKindValue` directly — not derived from the const object — so any new Go kind breaks compilation until the const and lookup tables are updated.

## File Map

### Stores

- **stores/clarificationStore.ts** — **useClarificationStore** — Pinia store managing the clarification queue. Holds the list of items (`items: ClarificationItem[]`), current index (`currentIndex`), pagination state (`total`, `loading`, `pendingCount`), and error handling. Provides `fetchQueue()` to load pending clarifications, `resolve()` to submit answers, `snooze()` to defer, `dismiss()` to remove. Computed: `currentItem`, `hasNext`, `isEmpty`, `progress`.

### Services

- **services/clarificationService.ts** — **clarificationService** — API client for all clarification endpoints. Methods: `queryQueue()` (fetch pending), `queryByID()` (single), `countPending()` (badge count), `resolve()` (POST answer), `snooze()` (POST hours), `dismiss()` (POST).

### Composables

- **composables/useClarification.ts** — **useClarification** — Thin wrapper over `useClarificationStore`. Calls `store.fetchQueue()` on mount, exposes reactive refs via `storeToRefs`, and provides `resolve`, `snooze`, `dismiss`, `refresh` methods. Pending count polling is handled globally by `AppSidebar` (60s interval) — not here.

### Views

- **views/ClarificationView.vue** — **ClarificationView** — Router entry point. Calls `useClarification()` (triggers `fetchQueue()` on mount), shows pending count in `PageHeader` subtitle, renders `ClarificationSession`.

### Components

- **components/clarifications/ClarificationCard.vue** — **ClarificationCard** — Single clarification card with kind-specific UI branches. Props: `item: ClarificationItem`. Emits: `resolve(answer)`, `snooze(hours)`, `dismiss`. Computes typed options via `contextAssignmentOptions: ContextAssignmentOptions | null` and `availableContexts: ContextRef[]`. Kind branches: context_assignment (suggest + alternate buttons), ambiguous_action (interpretation buttons from `AmbiguousActionOptions.interpretations`), ambiguous_deadline (datetime input), new_context (confirm/merge), debriefs (textarea), stale_task/inactivity_prompt (extend/note/close), voice_reference (text input), fallback (acknowledge).

- **components/clarifications/ClarificationSession.vue** — **ClarificationSession** — Queue navigator. Reads `currentItem`, `loading`, `isEmpty`, `progress`, `items` from store via `storeToRefs`. Shows LoadingSpinner while fetching, EmptyState when queue empty, otherwise renders current ClarificationCard with slide transition and navigation dots. Do NOT call `fetchQueue()` here — parent view's `useClarification()` handles it on mount.

### Types

- **types/clarification.ts** — **ClarificationItem**, **ClarificationAnswerOptions**, **ClarificationCountResponse** — Main data models. Re-exports the four option interfaces from `generated/clarification-options.ts`.
- **types/enums.ts** — **ClarificationKind**, **ClarificationStatus**, **ClarificationKindLabels**, **ClarificationKindColors** — Enums and lookup tables. `ClarificationKind` const uses `satisfies Record<string, ClarificationKindValue>` for Go-sync enforcement.
- **types/generated/clarification-kind.ts** — **ClarificationKindValue** — Union type, generated by `api/tooling/gen-ts-kinds`. DO NOT EDIT.
- **types/generated/clarification-options.ts** — **ContextRef**, **ContextAssignmentOptions**, **NewContextOptions**, **AmbiguousActionOptions**, **AmbiguousDeadlineOptions** — Typed option structs, generated by tygo. DO NOT EDIT.

### Tests

- **`__tests__/stores/clarificationStore.test.ts`** — Unit tests for store methods and computed properties.
- **`__tests__/components/clarifications/ClarificationCard.test.ts`** — Component tests for kind-specific UI branches and event emission.

## Impact Callouts

### ⚠ ClarificationItem (types/clarification.ts)

Changing this interface shape affects:

- **services/clarificationService.ts** — All response types (`queryQueue`, `queryByID`, `resolve`, `snooze`, `dismiss`) are typed as `ClarificationItem` or lists of it. Adding/removing/renaming fields requires API contract alignment.
- **stores/clarificationStore.ts** — State `items: ClarificationItem[]`; `fetchQueue()` populates from service; `removeAndAdvance()` mutates the array. Type shape changes require store refactoring.
- **components/clarifications/ClarificationCard.vue** — Props `item: ClarificationItem`, template accesses `item.kind`, `item.question`, `item.reasoning`, `item.createdAt`, `item.answerOptions`. Adding new kind-specific fields requires conditional UI updates.
- **components/clarifications/ClarificationSession.vue** — Receives `currentItem` from store as computed ref, passes to ClarificationCard. Shape changes propagate upward.
- **`__tests__/helpers/testFactories.ts`** — `makeClarificationItem()` builds test fixtures. If `answerOptions` changes type, factory must be updated (currently `null`).

### ⚠ ClarificationAnswerOptions (types/clarification.ts)

The typed union over four option interfaces. Changes affect:

- **components/clarifications/ClarificationCard.vue** — `options` computed returns `ClarificationAnswerOptions`. The `contextAssignmentOptions` computed narrows to `ContextAssignmentOptions | null`. The ambiguous_action branch casts to `AmbiguousActionOptions | null` to access `.interpretations`. Adding a new typed kind requires a new narrowing computed and cast.
- **`__tests__/types/clarification-options.test.ts`** — Regression test verifies the union accepts `ContextAssignmentOptions`. Must update if union changes.

### ⚠ ClarificationKind (types/enums.ts)

Changing the enum (adding/removing kinds) affects:

- **components/clarifications/ClarificationCard.vue** — Each kind has a dedicated `v-else-if="item.kind === ClarificationKind.XXX"` branch. Adding a kind requires a new branch; removing one requires deleting the branch and its options handling.
- **types/generated/clarification-kind.ts** — Must match backend kinds. Generated file drives the `satisfies` constraint: if `ClarificationKind` const contains a value not in `ClarificationKindValue`, TypeScript errors at compile time. Regenerate with `make generate-kinds` after backend changes.
- **ClarificationKindLabels** and **ClarificationKindColors** in `types/enums.ts` — Both are `Record<ClarificationKind, string>`, so TypeScript will error if a new kind is added to `ClarificationKindValue` but not to these maps. This is the intentional safety net.

### ⚠ ClarificationKindValue (types/generated/clarification-kind.ts)

Generated union. Changes require:

- Regenerate via `make generate-kinds` (runs `api/tooling/gen-ts-kinds`).
- Source of truth: `business/types/clarificationkind/clarificationkind.go` (Go).
- If kind count or spelling changes in Go, regenerate and commit. Because `enums.ts` uses `satisfies Record<string, ClarificationKindValue>`, adding a Go kind that doesn't exist in the const object causes a TS error; adding to the const before regenerating also causes a TS error.

### ⚠ Option Type Interfaces (types/generated/clarification-options.ts)

Generated by tygo from Go `options.go`. Changes require:

- Add/update Go struct in `business/domain/clarificationbus/options.go`.
- Regenerate via `make generate-options` (runs tygo).
- **components/clarifications/ClarificationCard.vue** uses `ContextAssignmentOptions` for `suggested_context` and `available_contexts` — field renames break the narrowing computeds directly (compile-time error now, not silent runtime failure).
- **components/clarifications/ClarificationCard.vue** casts to `AmbiguousActionOptions` for `.interpretations` — renaming `interpretations` in Go breaks the template loop (compile-time error via vue-tsc).
- **types/clarification.ts** — `ClarificationAnswerOptions` union must include any new option type; otherwise the new kind's options can't be used in a typed manner.

### ⚠ useClarificationStore (stores/clarificationStore.ts)

Single source of truth for queue state. Changes affect:

- **composables/useClarification.ts** — Destructures via `storeToRefs(store)`. Adding/removing state or computed refs requires updating the destructure and the composable's return value.
- **components/clarifications/ClarificationSession.vue** — Uses `storeToRefs(store)` directly for `currentItem`, `loading`, `isEmpty`, `progress`, `items`. Also calls `store.resolve()`, `store.snooze()`, `store.dismiss()`, `store.goTo()`. Method signature changes break session wiring.
- **views/ClarificationView.vue** — Calls `useClarification()` which calls `store.fetchQueue()` on mount. Signature changes propagate.

### ⚠ ClarificationCard (components/clarifications/ClarificationCard.vue)

Props and emits are a contract with the parent. Changes affect:

- **components/clarifications/ClarificationSession.vue** — Passes `:item="currentItem"` and listens to `@resolve`, `@snooze`, `@dismiss`. If props/emits change, session wiring breaks.
- Answer structure (`Record<string, unknown>`) emitted on resolve must match backend expectation. Adding typed answer parameters requires backend coordination.

## Cross-Domain Dependencies

Files outside the clarification domain that this feature depends on:

- **stores/toastStore.ts** — `useClarificationStore` calls `toast.error()`, `toast.success()` on API results.
- **types/query.ts** — `QueryResult<T>` and `ListParams` used in `clarificationService` for list query types.
- **services/client.ts** — Base HTTP `request()` function. All API calls go through it.
- **components/shared/LoadingSpinner.vue**, **components/shared/EmptyState.vue** — UI primitives imported by ClarificationSession.
- **components/layout/PageHeader.vue** — Used by ClarificationView for title/subtitle/actions.

Files outside the clarification domain that depend on clarification:

- **AppSidebar** (or equivalent navigation) — Polls `clarificationService.countPending()` on a 60s interval for the badge count. Uses `pendingCount` from the store.
- **views/ClarificationView.vue** — Router entry point that mounts the session and initializes queue loading.

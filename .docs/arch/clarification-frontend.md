# Clarification System — Frontend

> The clarification queue is a user-facing workflow that surfaces decision points generated by the backend's clarification engine. The frontend displays clarifications sorted by priority, handles kind-specific UI for different clarification types (context assignment, deadlines, debriefs, etc.), collects user responses, and sends them back to the API. The system uses Pinia for state management and handles both single-item resolution and batch queue navigation.

## Core Types

### ClarificationItem (types/clarification.ts)
```typescript
interface ClarificationItem {
  id: string
  kind: ClarificationKind
  status: ClarificationStatus
  subjectType: string
  subjectId: string
  question: string
  claudeGuess?: Record<string, unknown>
  reasoning?: string
  answerOptions: Record<string, unknown>
  answer?: Record<string, unknown>
  priorityScore: number
  snoozedUntil?: string
  createdAt: string
  resolvedAt?: string
}
```

Main model transported between API and frontend. The `kind` enum determines which UI component branch renders. The `answerOptions` object is kind-specific JSON that varies by type.

### ClarificationKind (types/enums.ts)

### ClarificationStatus (types/enums.ts)
```typescript
export const ClarificationStatus = {
```

Status lifecycle: pending → (resolved | snoozed | dismissed).

### Option Types (types/generated/clarification-options.ts)
```typescript
interface ContextRef {
  id: string
  title: string
}

interface ContextAssignmentOptions {
  suggested_context: string
  confidence: number
  available_contexts: ContextRef[]
}

interface NewContextOptions {
  context_id: string
  title: string
}

interface AmbiguousActionOptions {
  interpretations: string[]
}

interface AmbiguousDeadlineOptions {
  description: string
  raw_date: string
}
```

Generated by tygo from Go `business/domain/clarificationbus/options.go`. Each kind's `answerOptions` deserializes to one of these typed structures. Only the most complex kinds are typed; others (stale task, voice reference, debriefs, etc.) use generic `Record<string, unknown>`.

### ClarificationCountResponse (types/clarification.ts)
```typescript
interface ClarificationCountResponse {
  count: number
}
```

API response for pending clarifications count (badge on navigation).

### ClarificationQueryResponse (services/clarificationService.ts)
```typescript
interface ClarificationQueryResponse {
  items: ClarificationItem[]
  total: number
  page: number
  rowsPerPage: number
}
```

Wrapper for list queries. Returned from `/api/v1/clarifications` with pagination metadata.

## File Map

### Stores

- **stores/clarificationStore.ts** — **useClarificationStore** — Pinia store managing the clarification queue. Holds the list of items (`items`), current index (`currentIndex`), pagination state (`total`, `loading`), and error handling. Provides `fetchQueue()` to load pending clarifications, `resolve()` to submit answers, `snooze()` to defer, and `dismiss()` to mark as resolved. Computed properties expose `currentItem`, `hasNext`, `progress`, and `isEmpty`.

### Services

- **services/clarificationService.ts** — **clarificationService** — API client for all clarification endpoints. Methods: `queryQueue()` (fetch pending), `queryByID()` (single), `countPending()` (badge count), `resolve()` (POST answer), `snooze()` (POST hours), `dismiss()` (POST).

### Components

- **components/clarifications/ClarificationCard.vue** — **ClarificationCard** — Single clarification card with kind-specific UI branches. Renders kind label, age, question, reasoning, and action buttons tailored to each kind. Handles context_assignment with button for each option, ambiguous_action with interpretation buttons, ambiguous_deadline with datetime input, new_context with confirm/merge buttons, debriefs with textarea, stale_task/inactivity_prompt with action choices (extend/note/close), voice_reference with text input. Emits `resolve`, `snooze`, `dismiss` events.

- **components/clarifications/ClarificationSession.vue** — **ClarificationSession** — Queue navigator. Displays loading spinner while fetching, empty state when queue is empty, otherwise shows progress (e.g., "1 of 5"), the current card via transition, and navigation dots to jump between items. Wires store state to card events. Do NOT call `fetchQueue()` here — parent view handles it on mount.

### Types (Root)

- **types/clarification.ts** — **ClarificationItem**, **ClarificationCountResponse** — Main data models.
- **types/enums.ts** — **ClarificationKind**, **ClarificationStatus**, **ClarificationKindLabels**, **ClarificationKindColors** — Enums and lookup tables for display.
- **types/generated/clarification-kind.ts** — **ClarificationKindValue** — Union type, generated by `api/tooling/gen-ts-kinds`.
- **types/generated/clarification-options.ts** — Typed option structures, generated by tygo.

## Impact Callouts

### ⚠ ClarificationItem (types/clarification.ts)

Changing this interface shape affects:

- **services/clarificationService.ts** — All response types (`queryQueue`, `queryByID`, `resolve`, `snooze`, `dismiss`) are typed as `ClarificationItem` or lists of it. Adding/removing/renaming fields requires API contract alignment.
- **stores/clarificationStore.ts** — State `items: ClarificationItem[]`, logic in `fetchQueue()` populates from service, `removeAndAdvance()` manipulates the array. Type shape changes require store refactoring.
- **components/clarifications/ClarificationCard.vue** — Props `item: ClarificationItem`, template accesses `item.kind`, `item.question`, `item.reasoning`, `item.createdAt`, `item.answerOptions`. Adding new kind-specific fields requires conditional UI updates.
- **components/clarifications/ClarificationSession.vue** — Receives `currentItem` from store as computed ref, passes to ClarificationCard. Any shape change propagates upward.

### ⚠ ClarificationKind (types/enums.ts)

Changing the enum (adding/removing kinds) affects:

- **components/clarifications/ClarificationCard.vue** — Each kind has a dedicated `v-if="item.kind === ClarificationKind.XXX"` branch rendering kind-specific UI. Adding a kind requires a new branch; removing one requires deleting the branch.
- **types/generated/clarification-kind.ts** — Must match backend kinds. Any mismatch indicates schema divergence. Regenerate with `make generate-kinds` after backend changes.
- **types/enums.ts** lookup tables (**ClarificationKindLabels**, **ClarificationKindColors**) — Adding a kind requires entries in both maps or card rendering breaks (displays `undefined` label/color).
- **services/clarificationService.ts** — No direct dependency, but filtering queries by kind would break if maps are incomplete.

### ⚠ ClarificationKindValue (types/generated/clarification-kind.ts)

Generated union type. Changes require:

- Regenerate via `make generate-kinds` (runs `api/tooling/gen-ts-kinds`).
- Source of truth: `business/types/clarificationkind/clarificationkind.go` (Go).
- If kind count or spelling changes in Go, regenerate and commit the TypeScript file.
- Used for strict typing in API request/response bodies (answer payloads).

### ⚠ Option Type Interfaces (types/generated/clarification-options.ts)

Generated by tygo from Go `options.go`. Changes require:

- Add/update Go struct in `business/domain/clarificationbus/options.go`.
- Regenerate via `make generate-options` (runs tygo).
- **components/clarifications/ClarificationCard.vue** deserializes `answerOptions` per kind (e.g., `available_contexts` for context_assignment). If option struct fields change, card logic breaks unless updated.
  - Example: `suggestedContextId` computed extracts `.suggested_context` from options. If renamed in Go, computed breaks.
  - Example: `availableContexts` filters `(options.value as Record<string, unknown>).available_contexts`. If renamed/removed, nullish result causes silent failures.

### ⚠ useClarificationStore (stores/clarificationStore.ts)

The single source of truth for queue state. Changes affect:

- **components/clarifications/ClarificationSession.vue** — Uses `storeToRefs(store)` to expose `currentItem`, `loading`, `isEmpty`, `progress`, `items`. Adding/removing computed properties or state requires template updates.
- **views/ClarificationView.vue** (parent) — Calls `store.fetchQueue()` on mount and `store.fetchPendingCount()` for badge. Method signature changes break view.
- Any parent or sibling component that imports the store.

### ⚠ ClarificationCard (components/clarifications/ClarificationCard.vue)

Props and emits are contract with parent. Changes affect:

- **components/clarifications/ClarificationSession.vue** — Passes `:item="currentItem"` and listens to `@resolve`, `@snooze`, `@dismiss`. If props/emits change, session wiring breaks.
- Answer structure (`Record<string, unknown>`) emitted on resolve must match backend expectation. Adding typed answer parameters requires backend coordination.

## Cross-Domain Dependencies

Files outside the clarification domain that this feature depends on:

- **stores/toastStore.ts** — `useClarificationStore` calls `toast.error()`, `toast.success()` on API results. If toast store changes, error/success messaging breaks.
- **types/query.ts** — `QueryResult<T>` type used in service for list response structure.
- **services/client.ts** — Base HTTP request function. All API calls go through `request()`. If client auth/error handling changes, all clarification calls are affected.
- **components/shared/LoadingSpinner.vue**, **components/shared/EmptyState.vue** — UI components imported by ClarificationSession. If they change props/styling, session layout breaks.

Files outside the clarification domain that depend on clarification:

- **components/navigation/TopNav.vue** or similar — Displays pending count badge. Calls `clarificationService.countPending()` or watches store's `pendingCount`. If clarification types change, badge logic may break.
- **views/ClarificationView.vue** (parent) — Router view that mounts ClarificationSession. Initializes the store and calls fetch on mount.

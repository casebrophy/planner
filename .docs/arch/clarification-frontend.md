# Clarification System (Frontend)

> The clarification system surfaces AI-generated questions that need human input before the planner can confidently act. Each `ClarificationItem` has a `kind` that determines what answer UI to show (context picker, ambiguous action selection, debrief textarea, etc.). Items are fetched as a prioritized queue; the user works through them one at a time in `ClarificationSession` → `ClarificationCard`. Resolving, snoozing, or dismissing removes the item and advances the cursor.

## Core Types

### `ClarificationItem` (types/clarification.ts)
```ts
interface ClarificationItem {
  id: string
  kind: ClarificationKind           // discriminator — drives UI branch in ClarificationCard
  status: ClarificationStatus       // 'pending' | 'resolved' | 'snoozed' | 'dismissed'
  subjectType: string               // e.g. 'task', 'context'
  subjectId: string
  subjectDescription: string        // shown below question when non-empty
  question: string                  // human-readable question rendered as card heading
  claudeGuess?: Record<string, unknown>
  reasoning?: string                // shown as subtitle if present
  answerOptions: ClarificationAnswerOptions  // typed payload per kind
  answer?: Record<string, unknown>  // set after resolve
  priorityScore: number
  snoozedUntil?: string
  createdAt: string
  resolvedAt?: string
}
```

## File Map

### Services
- `services/clarificationService.ts` — **clarificationService** — REST client for all clarification endpoints
  - `queryQueue(params?)` → `QueryResult<ClarificationItem>` — GET `/api/v1/clarifications?status=pending&rows=50`
  - `queryByID(id)` → `ClarificationItem` — GET `/api/v1/clarifications/:id`
  - `countPending()` → `number` — GET `/api/v1/clarifications/count`
  - `resolve(id, answer)` → `ClarificationItem` — POST `.../resolve`
  - `snooze(id, hours=24)` → `ClarificationItem` — POST `.../snooze`
  - `dismiss(id)` → `ClarificationItem` — POST `.../dismiss`

### Stores
- `stores/clarificationStore.ts` — **useClarificationStore** — Pinia store managing queue cursor + pending badge
  - State: `items: ClarificationItem[]`, `total`, `loading`, `error`, `currentIndex`, `pendingCount`
  - Computed: `currentItem` (items[currentIndex] ?? null), `hasNext`, `isEmpty`, `progress {current, total}`
  - Actions: `fetchQueue(force?)`, `fetchPendingCount()`, `resolve(id, answer)`, `snooze(id, hours)`, `dismiss(id)`, `goTo(idx)`, `removeAndAdvance(id)`
  - `removeAndAdvance`: splices item from `items[]`, clamps `currentIndex`, decrements `pendingCount`
  - toast.success/error called on every action

### Composables
- `composables/useClarification.ts` — **useClarification** — thin view-model composable used by `ClarificationView`
  - Calls `store.fetchQueue()` on `onMounted`
  - Re-exports reactive refs (`items`, `total`, `loading`, `error`, `currentItem`, `isEmpty`, `progress`, `pendingCount`) + store actions
  - Does NOT poll `pendingCount` — that is `AppSidebar`'s responsibility (60 s interval)

### Views
- `views/ClarificationView.vue` — **ClarificationView** — route-level page component
  - Owns `useClarification()` which triggers the initial `fetchQueue()` on mount
  - Renders `PageHeader` with `pendingCount` subtitle and a Refresh button
  - Delegates all queue rendering to `<ClarificationSession />`

### Components
- `components/clarifications/ClarificationSession.vue` — **ClarificationSession** — queue navigator
  - Reads `currentItem`, `loading`, `isEmpty`, `progress`, `items`, `currentIndex` from `useClarificationStore`
  - Does NOT call `fetchQueue` (owned by parent `ClarificationView` → `useClarification`)
  - Renders: LoadingSpinner → EmptyState → progress counter + ClarificationCard with slide transition + progress dots
  - Progress dots: `store.goTo(idx)` on click; active dot = `currentIndex`
  - Forwards `@resolve`, `@snooze`, `@dismiss` events to store methods
- `components/clarifications/ClarificationCard.vue` — **ClarificationCard** — single-item answer UI
  - Props: `item: ClarificationItem`
  - Emits: `resolve(answer: Record<string, unknown>)`, `snooze(hours: number)`, `dismiss()`
  - Local state: `debriefAnswer`, `showNoteInput`, `noteText`, `newContextTitle`, `newContextKind`, `isCreating`, `createError`
  - Branches on `item.kind` for kind-specific UI:
    - **context_assignment** — "Confirm: \<suggested\>" (emerald) + alt context buttons (indigo) + create-new form with title input, Project/Area kind toggle, and `+` button; calls `contextService.create()` then `resolveWithValue({ context_id })`. All buttons disabled while `isCreating`.
    - **inactivity_prompt / stale_task** — "Still active" / "Add note" / "Close"; note reveals textarea + Submit
    - **ambiguous_action** — one button per `AmbiguousActionOptions.interpretations[]`, resolves `{ selected: idx }`
    - **ambiguous_deadline** — `datetime-local` input, resolves `{ due_date: ISO string }`
    - **new_context** — Confirm / Merge buttons
    - **context_debrief / task_debrief** — textarea + Submit, resolves `{ response: text }`
    - **voice_reference** — text input, resolves `{ resolved_text }` on Enter
    - **entity_link** — shows `source_type → target_type` with confidence %; Confirm Link / Reject buttons; resolves `{ confirmed: true/false }`
    - **type_assignment** — shows original `clause_text`, AI's `predicted_type` + confidence %, then one colored button per option (task=emerald, note=violet, event=blue, other=gray); resolves `{ type: opt }`
    - **event_prep** — informational; shows event/task overlap; Acknowledge button (fallback branch), resolves `{ acknowledged: true }`
    - **knowledge_gap** — shows `suggested_question` and `existing_knowledge_summary`; textarea for user to input the missing information; resolves `{ answer: text }`
    - **fallback** — Acknowledge button, resolves `{ acknowledged: true }`
  - Always-visible footer: Snooze 24h + Dismiss buttons; both disabled while `isCreating`
  - Free-text override (always visible): "None of these? Type your own" toggle that reveals text input for any kind; resolves `{ free_text: text }` on submit; resets on item prop change via `watch(() => props.item)`
  - `createAndResolve()` is the only place a cross-domain API call (contextService) originates from this component

## Impact Callouts

### ⚠ ClarificationItem (types/clarification.ts)
Changing this interface shape affects:
- `stores/clarificationStore.ts` — `items: ref<ClarificationItem[]>`, `currentItem` computed, all action params
- `composables/useClarification.ts` — re-exports `currentItem` reactive ref
- `services/clarificationService.ts` — all methods return or accept `ClarificationItem`
- `components/clarifications/ClarificationSession.vue` — passes `currentItem` as `:item` prop; iterates `items[]` for progress dots
- `components/clarifications/ClarificationCard.vue` — reads `item.kind`, `item.question`, `item.reasoning`, `item.answerOptions`, `item.createdAt` in template + computed

### ⚠ ContextAssignmentOptions / ContextRef (types/generated/clarification-options.ts)
Changing these generated types affects:
- `components/clarifications/ClarificationCard.vue` — `contextAssignmentOptions` computed cast, `availableContexts` iterates `available_contexts[]`, `suggestedContextId` reads `suggested_context`, template renders `c.id` and `c.title` on ContextRef items
- `services/clarificationService.ts` — `ClarificationItem.answerOptions` is serialized in API responses

### ⚠ AmbiguousActionOptions (types/generated/clarification-options.ts)
- `components/clarifications/ClarificationCard.vue` — template casts `options` to `AmbiguousActionOptions | null`, renders `.interpretations[]` as buttons

### ⚠ TypeAssignmentOptions (types/generated/clarification-options.ts)
- `components/clarifications/ClarificationCard.vue` — `typeAssignmentOptions` computed cast; template renders `.clause_text`, `.predicted_type`, `.confidence`, and `.options[]` as colored buttons; resolves `{ type: opt }`

### ⚠ VoiceReferenceOptions (types/generated/clarification-options.ts)
- `components/clarifications/ClarificationCard.vue` — voice_reference branch renders text input; resolves `{ resolved_text: value }` on Enter. Options struct provides context (original_text, reference_type, clause_text) but the current card UI uses only the text input for resolution.

### ⚠ EventPrepOptions (types/generated/clarification-options.ts)
- AUTO-GENERATED from `business/domain/clarificationbus/options.go`; created by `dailyplanapp.createEventPrepClarifications()` post-generation
- `components/clarifications/ClarificationCard.vue` — handled by fallback branch (Acknowledge); `event_prep` is informational, no side-effect on resolve
- `types/enums.ts` — `ClarificationKindLabels` and `ClarificationKindColors` must include `event_prep`

### ⚠ KnowledgeGapOptions (types/generated/clarification-options.ts)
- AUTO-GENERATED from `business/domain/clarificationbus/options.go`
- `components/clarifications/ClarificationCard.vue` — renders `suggested_question` and `existing_knowledge_summary` in template; textarea for user input; resolves `{ answer: text }` on submit
- `types/enums.ts` — `ClarificationKindLabels` and `ClarificationKindColors` must include `knowledge_gap`

### ⚠ ClarificationKind enum (types/enums.ts)
Adding or removing a kind affects:
- `components/clarifications/ClarificationCard.vue` — every `v-if/v-else-if` branch on `item.kind`; uses `ClarificationKindLabels` and `ClarificationKindColors` lookups
- `types/enums.ts` — `ClarificationKindLabels` and `ClarificationKindColors` are exhaustive `Record<ClarificationKind, ...>` — TypeScript compilation fails if a new kind is missing from either map
- `types/generated/clarification-kind.ts` — source of truth; must be regenerated (`api/tooling/gen-ts-kinds`) when Go enum changes

### ⚠ ClarificationStatus (types/enums.ts)
- `services/clarificationService.ts` — `queryQueue` hardcodes `status: 'pending'` in params
- `stores/clarificationStore.ts` — `fetchQueue` passes `{ status: 'pending', rows: 50 }`

## Cross-Domain Dependencies

- `services/contextService.ts` — imported directly by `ClarificationCard.vue` to call `contextService.create()` when user creates a new context from a `context_assignment` clarification; result `ctx.id` is used as the resolve answer
- `stores/toastStore.ts` — used by `clarificationStore` for all success/error toast notifications
- `components/shared/LoadingSpinner.vue` — used by `ClarificationSession`
- `components/shared/EmptyState.vue` — used by `ClarificationSession`
- `components/layout/PageHeader.vue` — used by `ClarificationView`
- `AppSidebar` — owns `fetchPendingCount()` polling (60 s interval); `ClarificationView`/`useClarification` does NOT poll the badge count
- `types/query.ts` — `QueryResult<T>`, `ListParams` interfaces used in service layer
- `types/enums.ts` — `ClarificationKind`, `ClarificationStatus`, `ClarificationKindLabels`, `ClarificationKindColors`, `ContextKind` (used in `ClarificationCard` for new-context kind selector)
